# v1.17.0

Adds two optional subtitle passes — speaker diarization, which labels who is speaking, and subtitle segmentation, which re-cuts Whisper's long segments into cues that follow subtitle norms. Each detected speaker can then be given a real name in the subtitle editor, and the transcript is now written to disk as soon as Whisper finishes rather than only at the end of the run. The app also learns to install new Python dependencies into an environment it already created.

新增兩個選用的字幕處理階段——講者辨識（標上是誰在說話）與字幕切段（把 Whisper 過長的段落重新切成符合字幕規範的短句）。辨識出的每位講者都可以在字幕編輯器裡取真實姓名，而逐字稿現在在 Whisper 一跑完就寫入磁碟，不再等到整趟結束。此外也讓 App 能把新的 Python 依賴裝進既有的環境裡。

## Added / 新增

- **Speaker diarization** ([python/whisperflow/diarization.py](python/whisperflow/diarization.py), [python/whisperflow/models/diarization_models.py](python/whisperflow/models/diarization_models.py), [python/whisperflow/transcriber.py](python/whisperflow/transcriber.py), [python/whisperflow/subtitles/writers.py](python/whisperflow/subtitles/writers.py), [python/whisperflow/config.py](python/whisperflow/config.py), [python/config/config.example.json](python/config/config.example.json), [python/config/config.metadata.json](python/config/config.metadata.json), [locales/*/settings.json](locales/zh-TW/settings.json)) — a new Speaker diarization card in Settings turns on a pass that runs after Whisper and prefixes each cue with `[Speaker 1]`. The engine is [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) on ONNX Runtime, which brings one ~10 MB dependency and needs neither torch nor a Hugging Face token — deliberately not `pyannote.audio`, whose `torch>=2.8` requirement has no macOS x86_64 wheel and would make the Intel Mac build uninstallable. The pyannote segmentation-3.0 and 3D-Speaker CAM++ models (~34 MB total) download into `<models_dir>/diarization/` on first use, verified against published sha256 digests and written through a temp file so an interrupted download leaves nothing behind. Speaker count can stay on automatic -- which is the better default, since an over-clustering repair pass now runs after the engine's own clustering -- or be pinned when you know it, in which case it is honoured as a minimum that the repair will not merge below, and a segment that spans a hand-over is split in two at the word boundary while keeping Whisper's own outer timestamps. Labels are applied at write time and never stored in the text, so the JSON output keeps a clean `text` and nothing has to parse `[...]` back out of a subtitle line — which would be ambiguous, since Whisper emits `[Music]` / `[音樂]` of its own.
  **講者辨識** — Settings 新增「講者辨識」卡片，啟用後會在 Whisper 之後多跑一個階段，並在每句字幕前加上 `[Speaker 1]`。引擎採用跑在 ONNX Runtime 上的 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)，只帶入一個約 10 MB 的依賴，不需要 torch、也不需要 Hugging Face token——刻意不用 `pyannote.audio`，因為它要求的 `torch>=2.8` 沒有 macOS x86_64 wheel，會讓 Intel Mac 版裝不起來。pyannote segmentation-3.0 與 3D-Speaker CAM++ 模型（合計約 34 MB）會在首次使用時下載到 `<models_dir>/diarization/`，以官方公布的 sha256 驗證，並先寫入暫存檔再原子改名，因此下載中斷不會留下半成品。講者人數可維持自動判斷——由於引擎自己的分群之後現在會再跑一道過度分群修復，自動已經是較好的預設——已知時也可直接指定，而指定會被當成下限，修復不會把人數併到比它更少；一段話中途換人會依字的時間拆成兩段，同時保留 Whisper 原本的外側時間碼。標籤是在寫檔時才套上、從不寫進文字裡，所以 JSON 的 `text` 保持乾淨，也不需要從字幕行反向解析 `[...]`——那本來就有歧義，因為 Whisper 自己也會輸出 `[Music]` / `[音樂]`。

- **Speaker labels survive editing the subtitles** ([src/main/transcript-reader.js](src/main/transcript-reader.js), [src/main/subtitle-writer.js](src/main/subtitle-writer.js), [src/renderer/components/transcript-preview.js](src/renderer/components/transcript-preview.js), [src/renderer/components/subtitle-editor.js](src/renderer/components/subtitle-editor.js), [src/renderer/styles.css](src/renderer/styles.css)) — the preview and the subtitle editor show the speaker as a read-only chip in front of the text, and the editor carries it through so re-generated SRT / VTT / TXT keep the same prefix Python wrote. The label travels beside the text rather than inside it, which is what lets `patchJsonWithEdits` stay untouched and keeps the on-disk JSON free of speaker markup. The prefix format literal is pinned on both sides by a test that reads it out of the Python source, because a divergence would silently rewrite every cue on the first save.
  **編輯字幕後講者標籤不會消失** — 預覽與字幕編輯器會在文字前面以唯讀標籤（chip）顯示講者，編輯器也會把它帶下去，讓重新產生的 SRT / VTT / TXT 保留與 Python 相同的前綴。標籤是放在文字旁邊而非文字裡面，因此 `patchJsonWithEdits` 完全不用改，磁碟上的 JSON 也不會混入講者標記。前綴格式的字面值由一個會直接讀取 Python 原始碼的測試在兩邊同時釘住——一旦兩邊不一致，第一次存檔就會默默改寫每一句字幕。

- **Name the speakers a diarized run found** ([src/renderer/components/speaker-names-dialog.js](src/renderer/components/speaker-names-dialog.js), [src/renderer/lib/speaker-names.js](src/renderer/lib/speaker-names.js), [src/main/transcript-reader.js](src/main/transcript-reader.js), [src/main/subtitle-writer.js](src/main/subtitle-writer.js), [src/renderer/components/subtitle-editor.js](src/renderer/components/subtitle-editor.js)) — **Speaker names** in the subtitle editor toolbar lists every voice as a card: a name field, that speaker's total talk time, and their longest few turns with time codes, so you can tell who is who before naming them. Confirming rewrites the label everywhere in the file, across SRT, VTT, TXT and JSON. The names live in a top-level `speakers` block in the transcript's own JSON, mirroring `segmentation`, which is what makes them survive closing and reopening the editor — before this the label could only be changed globally through `speaker_label_template`, and the chip in the editor was a read-only `<span>` with `user-select: none`. It also means transcribing the file again clears them, for free and on purpose: Python rewrites the whole JSON from a result that has no such block, so a name can never be left attached to a cluster index that clustering has since reassigned. That failure would be silent, which is the one worth designing out — a name on the wrong person reads exactly like a name on the right one. The button is disabled, with the reason in its tooltip, when the transcript has no speaker numbers to group by: an SRT or VTT read back carries only start, end and text, and the label inside the cue text cannot be told apart from Whisper's own `[Music]`.
  **為講者辨識找到的發言者命名** — 字幕編輯器工具列的「**發言者姓名**」會把每個聲音列成一張卡片：姓名欄位、該講者的總發言時長，以及他最長的幾段話與時間碼，讓你在命名前先分辨誰是誰。按下確認後，整份檔案的標籤都會換成新名字，SRT、VTT、TXT、JSON 一致。姓名存在逐字稿 JSON 的頂層 `speakers` 區塊，與 `segmentation` 同一個模式，這正是它能熬過「關掉編輯器再開」的原因——在此之前標籤只能透過 `speaker_label_template` 整體改，而編輯器裡的晶片是一個帶 `user-select: none` 的唯讀 `<span>`。這也表示重新轉錄會清掉姓名，而且是免費且刻意的：Python 每次都以一個沒有該區塊的結果整份重寫 JSON，所以名字不可能被留在一個已經被重新指派的分群編號上。那種失敗是靜默的，而靜默正是最值得在設計上除掉的——名字貼在錯的人身上，看起來跟貼對一模一樣。若逐字稿沒有可供分組的講者編號，按鈕會停用並在 tooltip 說明原因：讀回一份 SRT 或 VTT 只有 start、end 與 text，而字幕文字裡的標籤與 Whisper 自己的 `[Music]` 無法區分。

- **Subtitle segmentation** ([python/whisperflow/subtitles/segmentation.py](python/whisperflow/subtitles/segmentation.py), [python/whisperflow/transcriber.py](python/whisperflow/transcriber.py), [python/whisperflow/config.py](python/whisperflow/config.py), [python/whisperflow/cli.py](python/whisperflow/cli.py), [python/whisperflow/events.py](python/whisperflow/events.py), [python/config/config.example.json](python/config/config.example.json), [python/config/config.metadata.json](python/config/config.metadata.json), [locales/*/settings.json](locales/zh-TW/settings.json)) — a new Subtitle segmentation card in Settings re-cuts every subtitle by word timestamp into cues that follow the published subtitle norms: at most 2 lines, at most 7 seconds, inside a reading-speed budget, never spanning two speakers. On the 64-minute talk the specification measured, 31% of 408 subtitles ran past 7 seconds and 38% needed three lines or more; the longest was 30 seconds, and the one at 36:18 packed 303 characters into 20.7 seconds. Segmentation drives both of those counts to zero by construction — the prototype the approach was validated with turned those 408 subtitles into 727 cues, so expect roughly 1.8× as many. Where to cut is chosen by a forward dynamic program over a whole run of speech rather than greedily, because the greedy choice is exactly what produces a full line followed by a two-word remnant: cost drops after sentence punctuation, then commas, then pauses — and the pause term is a ramp rather than a step, so a 0.28-second pause outranks a 0.02-second one, which is the only usable signal in unpunctuated Chinese — while fill is scored quadratically so cues come out evenly sized. Line widths are measured in half-width columns (`east_asian_width` W and F count 2, combining marks 0), so `max_line_width` keeps the unit of the language you are working in — 42 for Latin scripts, 16 for CJK, the published Netflix figures — and mixed Chinese–English text needs no second setting. A new `segmenting` stage drives the progress chip, and the run log ends with a one-line summary (cues in and out, how many broke a limit, how many were stretched, the longest) so a file that needed the single-word escape hatch for an unsplittable token says so instead of hiding it. The module imports nothing outside the standard library, not even numpy.
  **字幕切段** — Settings 新增「字幕切段」卡片，會以逐字時間碼把每句字幕重新切成符合業界字幕規範的短句：每則最多 2 行、最長 7 秒、不超過閱讀速度上限、絕不跨越兩個講者。以規格書實測的那場 64 分鐘演講為例，408 則字幕中有 31% 超過 7 秒、38% 需要 3 行以上，最長一則 30 秒，36:18 那一則更把 303 個字元塞進 20.7 秒。切段讓這兩個數字在結構上必然歸零——驗證這個做法的原型把那 408 則切成 727 則，所以可以預期數量大約變成 1.8 倍。切點是由整段語音的前向動態規劃決定，而不是貪婪選擇，因為貪婪正是「一行塞滿、只剩兩個字」的來源：成本在句尾標點後最低，其次是逗號，再其次是停頓——而停頓項是斜坡而非階梯，所以 0.28 秒的停頓勝過 0.02 秒的，這是無標點中文唯一可用的訊號——填充度則以二次式計分，讓切出來的每一則大小平均。行寬以半角欄位計算（`east_asian_width` 的 W 與 F 算 2 欄、組合字元算 0 欄），因此 `max_line_width` 維持你正在處理的語言自己的單位——拉丁文字 42、中日韓 16，就是 Netflix 公布的數字——中英混排也不需要第二個設定。新增的 `segmenting` 階段會驅動進度標籤，執行紀錄最後會印一行摘要（切前與切後的則數、幾則違反上限、幾則被延長、最長幾秒），讓需要動用「單字逃生出口」的檔案自己說出來，而不是藏起來。這個模組不 import 任何標準庫以外的東西，連 numpy 都沒有。

- **Incremental Python environment updates** ([src/main/venv-installer.js](src/main/venv-installer.js), [src/main/preflight-checker.js](src/main/preflight-checker.js), [src/main/ipc-handlers.js](src/main/ipc-handlers.js), [preload/preload.js](preload/preload.js), [src/renderer/lib/venv-bootstrap.js](src/renderer/lib/venv-bootstrap.js), [src/renderer/components/preflight-panel.js](src/renderer/components/preflight-panel.js), [locales/*/preflight.json](locales/zh-TW/preflight.json)) — the bundled venv was built once and never revisited, so an existing user whose `requirements.txt` gained an entry never installed it. A second marker file now records the sha256 of `requirements.txt`, and System Check offers **Update environment** when it no longer matches. It is a warning, never an error: a venv with stale dependencies still transcribes perfectly well, so blocking the run would have broken every existing user's first launch after upgrading. A pre-1.17 venv simply has no hash file, which reads as "needs updating" with no migration step and without changing what "environment ready" means anywhere else.
  **Python 環境可增量更新** — 內建 venv 以前建立一次就不再回頭看，所以既有使用者即使 `requirements.txt` 多了項目也永遠裝不到。現在會用第二個標記檔記下 `requirements.txt` 的 sha256，不一致時「系統檢查」會提供「更新環境」。這是警告而非錯誤：依賴過期的 venv 轉錄仍然完全正常，若擋下執行，每位既有使用者升級後第一次啟動都會被卡住。1.17 之前的 venv 單純就是沒有雜湊檔，這剛好被判定為「需要更新」，不需要任何遷移程式碼，也不會改變其他地方對「環境已就緒」的判斷。

## Changed / 變更

- **A speaker's name is printed once per turn, not on every cue** ([python/whisperflow/diarization.py](python/whisperflow/diarization.py), [python/whisperflow/transcriber.py](python/whisperflow/transcriber.py)) — diarization set `speaker_label` on every segment, so `[Speaker 1] ` was repeated on all 408 subtitles of the hour-long talk above while eating 12 of the 42 columns a Latin line gets. It is now set only on the first cue of a turn, and a turn is tracked across the pause-driven breaks segmentation introduces, so a speaker who stops for three seconds is not announced again. No JavaScript changed: `format_speaker_prefix` already returned `""` for an empty label and both the preview and the editor key their speaker chip off `speakerLabel`, so the chip became once-per-turn on its own.
  **講者名稱改成每輪只印一次，而非每則都印** — 講者辨識以前會在每一個段落都設 `speaker_label`，所以上面那場一小時演講的 408 則字幕每一則都重複一次 `[Speaker 1] `，而它在拉丁文字 42 欄的行寬裡就吃掉 12 欄。現在只在一輪的第一則設定，而且「同一輪」會跨越切段因停頓產生的分割，因此講者停頓三秒不會被重新標記。JavaScript 完全沒改：`format_speaker_prefix` 本來就對空標籤回傳 `""`，預覽與編輯器的講者 chip 也都以 `speakerLabel` 為條件，所以 chip 自動變成一輪一次。

- **The TXT transcript is written as speaker paragraphs** ([python/whisperflow/subtitles/writers.py](python/whisperflow/subtitles/writers.py), [src/main/subtitle-writer.js](src/main/subtitle-writer.js), [src/renderer/components/subtitle-editor.js](src/renderer/components/subtitle-editor.js), [src/main/ipc-handlers.js](src/main/ipc-handlers.js)) — a `.txt` of several hundred lines averaging six words each is useless as a transcript, which is the only thing a `.txt` is for. With segmentation on, consecutive cues are joined into a paragraph and a blank line is inserted when the speaker changes or more than two seconds of silence passes; a cue's own line break flattens to a space, and a space goes between two cues only when they are not both CJK. The rule is deliberately structural — no punctuation or language knowledge — because it has to hold identically in Python and in the editor's JavaScript, and four lines of structure cannot drift the way two heuristics would. With segmentation off the writer takes the original, untouched branch, so the output is byte-identical.
  **TXT 逐字稿改成以講者分段** — 幾百行、每行平均六個字的 `.txt` 作為逐字稿完全不能用，而逐字稿是 `.txt` 唯一的用途。開啟切段後，連續的字幕會併成一個段落，並在講者改變或靜音超過兩秒時插入空行；字幕自己的換行會攤平成空格，兩則之間只有在並非兩側皆為中日韓文字時才補空格。這個規則刻意只用結構條件、不碰標點與語言知識，因為它必須在 Python 與編輯器的 JavaScript 裡表現完全一致，而四行結構性邏輯不會像兩套啟發式那樣各自漂移。關閉切段時走的是原本未改動的分支，輸出逐位元組相同。

- **`result["text"]` is recomputed after the segments are rewritten** ([python/whisperflow/transcriber.py](python/whisperflow/transcriber.py), [python/whisperflow/subtitles/segmentation.py](python/whisperflow/subtitles/segmentation.py)) — the JSON output carries both a `segments` array and a flat `text`. Whisper fills `text` once, and nothing recomputed it when diarization replaced `segments`, so a diarized JSON already shipped a `text` that disagreed with its own segments. Both passes now rebuild it from the words they actually emitted.
  **`result["text"]` 會在段落被改寫後重算** — JSON 輸出同時帶有 `segments` 陣列與一個平鋪的 `text`。Whisper 只填一次 `text`，而講者辨識換掉 `segments` 後沒有任何地方重算它，所以開啟講者辨識的 JSON 早就帶著一個與自己的 segments 不符的 `text`。現在兩個階段都會以它們實際輸出的字重建這個欄位。

- **Subtitle writers always build cue text from the segment's own text** ([python/whisperflow/subtitles/writers.py](python/whisperflow/subtitles/writers.py)) — `_prepare_cues` used to re-join word tokens whenever a segment carried word timestamps. That branch was unreachable (word timestamps were never enabled) and wrong for the app's default language: with no token starting with a space, it fell through to `" ".join(...)` and turned `你好世界` into `你 好 世 界`. It is gone, so cue text now has a single source that is always stripped. `assign_speakers` rebuilds the text for each piece it splits off, so nothing needed the word-joining path.
  **字幕輸出器一律以段落本身的文字組成字幕** — `_prepare_cues` 以前在段落帶有逐字時間碼時會改用 words 重組文字。那條分支實際上執行不到（逐字時間碼從未被開啟），而且對 App 的預設語言是錯的：當沒有任何 token 以空白開頭時，它會落到 `" ".join(...)`，把 `你好世界` 變成 `你 好 世 界`。該分支已移除，字幕文字現在只有單一來源、且永遠經過 strip。`assign_speakers` 在拆段時已經重組好每一段的文字，不需要那條路徑。

- **Diarization changes segment boundaries slightly** ([python/whisperflow/transcriber.py](python/whisperflow/transcriber.py)) — turning it on enables faster-whisper's word timestamps, and `add_word_timestamps()` rewrites a segment's start / end from its first and last word and changes how the decode window advances. So diarized output is not "the same output plus labels". With diarization off the option is omitted entirely, faster-whisper's own default applies, and the output is byte-identical to v1.16.7.
  **開啟講者辨識會讓分段邊界略有變化** — 啟用後會開啟 faster-whisper 的逐字時間碼，而 `add_word_timestamps()` 會用第一個與最後一個字改寫段落的 start / end，也會改變解碼視窗的前進方式。因此辨識後的輸出並不是「原輸出加上標籤」。關閉時完全不會傳入該選項，沿用 faster-whisper 自己的預設值，輸出與 v1.16.7 逐位元組相同。

- **`vad=none` decodes audio through the ffmpeg CLI** ([python/whisperflow/transcriber.py](python/whisperflow/transcriber.py)) — this was the only path that handed a file path, rather than a decoded array, to faster-whisper, which then decoded it with PyAV. It now uses the same `load_audio()` every other VAD mode uses. Memory use is unchanged (the branch already fed the whole file to `transcribe()` in one call), and a file deleted mid-run now surfaces as the specific "input file no longer exists" error instead of a generic one.
  **`vad=none` 改用 ffmpeg CLI 解碼音訊** — 這是唯一把檔案路徑（而非已解碼陣列）交給 faster-whisper 的路徑，因此會由 PyAV 解碼。現在改用其他 VAD 模式都在用的同一個 `load_audio()`。記憶體用量不變（這條路徑本來就是把整個檔案一次送進 `transcribe()`），而轉錄期間檔案被刪除時，現在會顯示「輸入檔案已不存在」這個明確錯誤而非籠統的失敗。

## Fixed / 修正

- **Automatic speaker counting split one speaker into dozens on long recordings** ([python/whisperflow/diarization.py](python/whisperflow/diarization.py), [python/whisperflow/config.py](python/whisperflow/config.py), [python/whisperflow/cli.py](python/whisperflow/cli.py), [python/config/config.example.json](python/config/config.example.json), [python/config/config.metadata.json](python/config/config.metadata.json), [locales/*/settings.json](locales/zh-TW/settings.json)) — a 64-minute talk with about four speakers came back as **60**. sherpa-onnx clusters with complete linkage, hard-coded, and offers no size guard, so a single outlier embedding inside a cluster permanently vetoes every further merge — and the outlier population grows with recording length, because the C++ side admits an embedding from as little as 0.169 s of speech. Raising the clustering threshold does not help: 0.5 gives 60 speakers and 0.8 still gives 17. The same failure is published against the same stack elsewhere, and sherpa-onnx's own issue tracker has carried the question unanswered since 2024 with "you need to tune the threshold by yourself" as the only guidance. A repair pass now runs afterwards, in the order 3D-Speaker (who train the CAM++ model this uses) apply in their own clustering code: one embedding per turn, merge the clusters whose duration-weighted centroids agree, then fold away the fragments too short to be anybody. That talk now reports 4 speakers, and sherpa's own 57-second four-speaker sample still reports 4. The repair adds about 11 s to a 64-minute run. It can be switched off with the new **Repair over-clustering** setting, because with it on the clustering threshold has little effect — and a pinned speaker count is now honoured as a minimum the repair will not merge below.
  **長錄影的自動講者判斷會把一個人拆成好幾十位** — 一場約四位講者的 64 分鐘演講被判成 **60 位**。sherpa-onnx 的分群用的是寫死的完全連結法，而且完全沒有大小保護，所以群集裡只要有一個離群嵌入，就永久否決掉之後所有合併——而離群嵌入的數量隨錄影長度增加，因為 C++ 那側只要 0.169 秒的語音就會產生一個嵌入。調高分群門檻沒有用：0.5 得到 60 位、0.8 仍有 17 位。同樣的技術棧在別處也公開記錄了同一個現象，而 sherpa-onnx 自己的 issue 從 2024 年起就掛著這個問題沒有答案，唯一的指引是「請自己調門檻」。現在會在之後多跑一道修復，順序沿用 3D-Speaker（CAM++ 模型的訓練者）在他們自己的分群程式裡的做法：每段抽一個嵌入、把以時長加權的中心一致的群集併回來、再吸收掉短到不足以構成一個人的碎片。那場演講現在回報 4 位，而 sherpa 自己的 57 秒四人樣本仍然是 4 位。這道修復對 64 分鐘的執行約增加 11 秒。可以用新增的「**修復過度分群**」設定關掉，因為開啟時分群門檻幾乎沒有作用——而指定的講者人數現在會被當成修復不得低於的下限。

- **A failure in diarization or subtitle segmentation threw away the finished transcript** ([python/whisperflow/transcriber.py](python/whisperflow/transcriber.py)) — both stages run after Whisper and neither was guarded, so an exception from either propagated out of `run()` and `_write_outputs` never executed. A stage that only annotates the transcript could therefore destroy it: on a 64-minute recording that is most of an hour of compute discarded, with no subtitle file of any kind written and nothing on screen to say why they are missing. Both now run through one guard, which logs a warning naming the stage with its traceback and lets the writers run. What then reaches the writers is exactly the output the user would have got with the feature switched off, never a half-annotated one, because both stages compute their whole result before assigning it back — `assign_speakers` copies rather than mutating, and `apply_to_result` calls `resegment` first. The guard catches `Exception` and not `BaseException`, so cancelling a run still cancels it. The warning goes through the logger rather than an emitted `warning` event because the renderer has no consumer for that event type, so an emitted one would reach nobody.
  **講者辨識或字幕切段失敗會把已完成的逐字稿整個丟掉** — 這兩個階段都在 Whisper 之後執行，而且都沒有防護，所以任一個丟出例外都會傳出 `run()`，`_write_outputs` 永遠不會執行。於是一個只負責加註的階段就能摧毀逐字稿：在 64 分鐘的錄影上，那是將近一小時的運算被丟棄，任何格式的字幕檔都不會產生，畫面上也沒有任何訊息說明檔案為什麼不見。現在兩者都走同一道防護，它會記下一行指名該階段的警告（含 traceback），然後讓輸出器照常執行。此時送進輸出器的，正好就是使用者在關閉該功能時會得到的輸出，絕不會是半套加註的版本，因為這兩個階段都是先把結果算完才賦值回去——`assign_speakers` 是複製而非就地修改，`apply_to_result` 也是先呼叫 `resegment`。防護捕捉的是 `Exception` 而非 `BaseException`，所以取消執行仍然會真的取消。那行警告走的是 logger 而非發出 `warning` 事件，因為前端沒有任何地方消費這個事件型別，發了也沒人會收到。

- **A transcript existed only in memory until the very last step of the run** ([python/whisperflow/transcriber.py](python/whisperflow/transcriber.py)) — the pipeline was Whisper, then diarization, then segmentation, then one write at the end, so for most of an hour on a long recording there was nothing on disk at all. Anything that ended the process in that window — a kill, an out-of-memory, the parent app going away — cost the entire run, with no subtitle file of any kind to show for it. A measured case: a 64-minute recording reached 50 minutes of Whisper and produced nothing. The transcript is now written as soon as Whisper finishes, before the stages that only annotate it, and the final write replaces that copy. A run that dies after the landing leaves exactly what the user would have got with diarization and segmentation switched off, and a cancelled run now also keeps its transcript rather than discarding work that was already paid for. The second write deliberately replays the paths the first one resolved instead of resolving them again: under `overwrite_policy: skip` a fresh resolve would skip the real output as already-present — against the landing's own file — and leave the user with the un-annotated copy for good, and under `rename-suffix` it would put the annotated copy under a name nobody is looking for. Both are pinned by tests across all three policies.
  **逐字稿在整趟執行的最後一步之前只存在於記憶體** — 管線是 Whisper、講者辨識、字幕切段，最後才寫一次，所以長錄影有將近一小時的時間磁碟上什麼都沒有。任何在那段期間結束程序的事——被殺、記憶體不足、父程序消失——都讓整趟運算歸零，連一個字幕檔都沒有。實測案例：一支 64 分鐘的錄影跑到 50 分鐘，最後什麼都沒產出。現在 Whisper 一跑完就先寫一份，排在那些只負責加註的階段之前，最終寫入再取代它。在落地之後才死掉的執行，留下的正好就是使用者將辨識與切段關閉時會得到的東西；被取消的執行也不再丟掉已經付過代價的工作。第二次寫入刻意沿用第一次解析出的路徑而非重新解析：`overwrite_policy: skip` 時，重新解析會把真正的輸出當成「已存在」而跳過——而那個「已存在」的正是先落地那份——使用者就永遠只拿到未加註的版本；`rename-suffix` 則會把加註過的那份放在沒人在找的檔名下。兩種情況都有測試釘住，三種 policy 全測。

- **An orphaned run died at its next progress tick** ([python/whisperflow/events.py](python/whisperflow/events.py)) — Electron spawns the Python process and reads progress events off its stdout, but closing or killing the app does not kill the child: it keeps transcribing into a pipe with nobody on the other end. The write was unguarded, so the first event after the app went away raised `BrokenPipeError` and ended a run that was otherwise healthy and had a transcript still to write — and writing that transcript to disk needs no reader. The write now tolerates a dead stream and carries on, silently, because there is no channel left to report on and the logging handler writes to that same stdout. `flush` is inside the guard too: leaving it outside moves the failure one line down rather than fixing it, which only the end-to-end test catches.
  **失去父程序的執行會在下一次回報進度時死掉** — Electron 產生 Python 程序並從它的 stdout 讀進度事件，但關閉或殺掉 App 並不會連帶殺死子程序：它會繼續轉錄，寫進一条另一端已經沒有人的管線。那個寫入沒有任何防護，所以 App 消失後的第一個事件就會拋 `BrokenPipeError`，結束一個其實健康、而且還有逐字稿沒寫的執行——而把逐字稿寫到磁碟根本不需要讀者。現在寫入會容忍已死的串流並繼續跑，而且是安靜地——因為已經沒有通道可以回報，而 log 的 handler 寫的也是同一個 stdout。`flush` 也在防護裡面：把它留在外面只是把失敗往下移一行而不是修好它，而這件事只有端到端測試抓得到。

- **Renaming a speaker did not count as an unsaved change** ([src/renderer/components/subtitle-editor.js](src/renderer/components/subtitle-editor.js), [src/renderer/styles.css](src/renderer/styles.css)) — the editor's undo history holds cue text only, and the unsaved flag is derived from it, so a rename followed by an edit and an undo came back "clean": Save went dead and closing the editor did not even prompt, taking the rename with it. Names now carry a saved baseline of their own, which the unsaved flag, the Revert button and the close prompt all consult. Found while wiring the naming dialog, not by a test. Also in this file: `.toast-warning` did not exist in the stylesheet although the editor has been passing `'warning'` to `showToast` for the line-limit and no-formats-enabled cases, so both rendered as a transparent box with a pale border.
  **替講者改名不算「尚未儲存」** — 編輯器的復原歷史只持有字幕文字，而未儲存旗標是從它推導出來的，所以「改名 → 編輯 → 復原」之後狀態會變回「乾淨」：儲存鈕失效，關閉編輯器時也不會提示，改名就這樣消失。現在姓名有自己的已儲存基準，未儲存旗標、「復原」按鈕與關閉提示都會一併考慮。這是接線命名對話框時發現的，不是測試抓到的。同一檔順手補：樣式表裡根本沒有 `.toast-warning`，而編輯器在行數上限與「未啟用任何輸出格式」兩種情況下都在傳 `'warning'`，兩者都渲染成透明的框。

- **Setting a max line width deleted the spaces between words** ([python/whisperflow/subtitles/writers.py](python/whisperflow/subtitles/writers.py)) — `_wrap_tokens` split on `" "` and then appended tokens with `current += token`, never putting the separator back, so a wrapped Latin line came out as `Hellotherefriend`. Nobody had hit it, because `config.example.json` seeds `max_line_width` blank and blank means "don't wrap" — the function was unreachable in a default install. An existing test was asserting the broken output, with a comment saying it was pre-existing behaviour left alone. Line wrapping was about to become load-bearing, so both are fixed. Anyone who had set a line width gets different — correct — output after upgrading.
  **設定每行字數上限會把單字之間的空白刪掉** — `_wrap_tokens` 以 `" "` 切開，再用 `current += token` 接起來，從來沒把分隔符補回去，所以折行後的拉丁文字會變成 `Hellotherefriend`。沒有人踩到，是因為 `config.example.json` 把 `max_line_width` seed 成空白、而空白表示「不折行」——在預設安裝下這個函式根本到不了。還有一個既有測試正在斷言這個壞掉的輸出，註解寫著「這是既有行為，此處不動」。折行即將變成關鍵路徑，所以兩者都修了。原本有設定行寬的人升級後會得到不同的——正確的——輸出。

- **Editing subtitles wrote to the wrong JSON segments after a blank one** ([src/main/subtitle-writer.js](src/main/subtitle-writer.js)) — the editor reads segments through a `.filter(s => s.text)` that drops blank ones, but `patchJsonWithEdits` wrote back by array index, so a single empty segment shifted every later edit onto the wrong segment — silently, because the two arrays have the same shape and a `Math.min` hid the length mismatch. Patching now matches on a cue's start time to the millisecond, queues duplicates, and falls back to the index only when a start time is unusable; timestamps are read-only in the editor, so start time is a stable key. Segmentation roughly doubles the number of cues, and a user who edits one cue to empty creates the condition themselves.
  **編輯字幕時，空白段落之後的編輯會寫到錯的 JSON 段落** — 編輯器讀取段落時會經過 `.filter(s => s.text)` 丟掉空白的，但 `patchJsonWithEdits` 是按陣列索引寫回，因此只要有一個空段落，後續每一筆編輯都會落到錯的段落上——而且完全無聲，因為兩個陣列同型，`Math.min` 又把長度不符藏了起來。現在改以字幕起始時間（毫秒精度）比對、時間重複時用佇列處理，只有在起始時間不可用時才退回索引；編輯器裡時間碼是唯讀的，所以起始時間是穩定的鍵。切段讓字幕數量大約翻倍，而使用者只要把某一則編輯成空白，就會自己製造出這個條件。

- **Two-line subtitles were squashed onto one line in the preview** ([src/renderer/styles.css](src/renderer/styles.css), [src/renderer/components/subtitle-editor.js](src/renderer/components/subtitle-editor.js), [src/renderer/components/transcript-preview.js](src/renderer/components/transcript-preview.js)) — the preview put cue text into a DOM text node with the line break intact and then lost it to the default `white-space`, which collapses a newline to a space; `.transcript-segment-text` now sets `pre-line`, which honours the break while still collapsing runs of spaces, so nothing else about the layout moves. The editor was worse: it flattened line breaks on load, for the stored original as well as the draft, so not even Undo could bring them back, and Enter was blocked outright. It now keeps the breaks, allows Enter up to the configured line count, refuses to create a blank line, and preserves the caret while normalising — the old handler reset `.value` on every keystroke, which jumped the cursor to the end on paste. Copy-all now joins segments with a blank line so multi-line cues stay legible once pasted.
  **兩行字幕在預覽裡被擠成一行** — 預覽把字幕文字放進 DOM text node 時換行是完好的，卻被 `white-space` 的預設值收合成空格；`.transcript-segment-text` 現在設為 `pre-line`，它會尊重換行但仍收合連續空白，因此版面其他部分不動。編輯器更嚴重：它在載入時就把換行攤平，而且保存的 original 跟 draft 都攤平，所以連「還原」都救不回來，Enter 也被完全封鎖。現在它會保留換行、在設定的行數上限內允許 Enter、拒絕產生空行，並在正規化時保住插入點——舊的處理器每次按鍵都重設 `.value`，貼上時游標會跳到結尾。「複製全部」現在以空行分隔各段，讓多行字幕貼出去之後仍然好讀。

- **Fresh installs failed to transcribe with `vad=none` on PyAV 19** ([python/requirements.txt](python/requirements.txt)) — av 19.0.0 removed the `metadata_errors` parameter from `av.open()`, but faster-whisper 1.2.1's `decode_audio()` still passes it, so any new install raised a TypeError the moment PyAV decoded anything. Pinned to `av<19` with the removal condition recorded in a comment; the ffmpeg-CLI change above is the second layer. Existing installs on av 19.x will be downgraded by the environment update, which costs one extra wheel download.
  **全新安裝在 PyAV 19 下使用 `vad=none` 會轉錄失敗** — av 19.0.0 移除了 `av.open()` 的 `metadata_errors` 參數，但 faster-whisper 1.2.1 的 `decode_audio()` 仍然會傳，導致新安裝只要走到 PyAV 解碼就丟 TypeError。已鎖定為 `av<19`，並在註解記下何時可以解除；上面的 ffmpeg CLI 改動是第二層保險。已經裝了 av 19.x 的環境會在更新時被降版，代價是多下載一個 wheel。

- **Localized error messages never reached the screen** ([src/renderer/components/error-state.js](src/renderer/components/error-state.js)) — `normalizeError()` rebuilt the payload field by field and dropped `titleKey` / `messageKey` / `messageParams`, which is exactly what the error banner and dialog resolve in preference to the legacy plain strings. Since those strings are empty on the run paths, the hard-coded `執行失敗` / `發生未預期錯誤。` fallbacks won every time, so every `errors:*` title and message wired through a run failure was dead copy regardless of UI language. The six i18n fields now pass through.
  **本地化的錯誤文案從來沒有顯示出來** — `normalizeError()` 逐欄重建 payload，卻漏掉 `titleKey` / `messageKey` / `messageParams`，而錯誤橫幅與對話框正是優先讀這幾個欄位、而非舊的純字串。由於執行路徑上那些純字串是空的，硬編碼的 `執行失敗` / `發生未預期錯誤。` 每次都勝出，所有接在執行失敗上的 `errors:*` 標題與訊息，無論 UI 語言是什麼都等於廢稿。現在這六個 i18n 欄位會完整傳遞。

- **The VAD stage chip read "Idle" for the whole step** ([src/renderer/components/queue-panel.js](src/renderer/components/queue-panel.js), [src/main/queue-manager.js](src/main/queue-manager.js), [src/renderer/components/console-log.js](src/renderer/components/console-log.js)) — Python emits the stage as `loading-vad`, but the chip's lookup table and the progress fallback only knew `vad`, so the chip fell back to "Idle" and no progress value applied while Silero VAD downloaded or loaded. All three maps now accept either spelling. Found by the new test that checks every stage constant against all five places a stage has to be wired up.
  **VAD 階段的狀態標籤整段顯示「待機」** — Python 送出的階段名稱是 `loading-vad`，但標籤的對照表與進度 fallback 只認得 `vad`，所以 Silero VAD 下載 / 載入期間標籤退回「待機」、也沒有進度值。三個對照表現在都接受兩種寫法。這是新增的測試在比對每個階段常數與五個必須接線的位置時發現的。

- **"Input file no longer exists" was unreachable in production** ([bridge/run_cli.py](bridge/run_cli.py)) — the only script Electron runs for transcription reported `reason` as the exception class name, while the main process dispatches on snake_case reasons, so the specific banner never matched and the error always arrived as a generic failure. The bridge now catches `InputFileVanishedError` explicitly, alongside the two new diarization failures.
  **「輸入檔案已不存在」在正式環境永遠不會出現** — Electron 轉錄時唯一執行的腳本把 `reason` 回報成例外的類別名稱，而 main process 比對的是 snake_case 的 reason，因此那個專屬橫幅永遠對不上，錯誤一律變成籠統的失敗。bridge 現在會明確捕捉 `InputFileVanishedError`，以及兩個新的講者辨識錯誤。

- **The environment-setup progress line showed Chinese in the English UI** ([src/renderer/lib/venv-bootstrap.js](src/renderer/lib/venv-bootstrap.js), [locales/*/events.json](locales/zh-TW/events.json)) — its stage labels were hard-coded Traditional Chinese literals, and three of its seven patterns could never match at all because they looked for our own English banners while the installer emits them translated. The three dead patterns are gone and the remaining four pip-native ones resolve through both locales.
  **建立環境的進度文字在英文介面顯示中文** — 階段標籤原本是硬編碼的繁體中文字串，而七個比對樣式中有三個根本不可能命中——它們比對的是我們自己的英文橫幅，但安裝程式送出的是翻譯後的文字。三個無效樣式已移除，剩下四個 pip 原生樣式改走雙語文案。

## Tests / 測試

- **Python suite grows from 74 to 306 tests** ([python/whisperflow/tests/test_segmentation.py](python/whisperflow/tests/test_segmentation.py), [python/whisperflow/tests/test_diarization.py](python/whisperflow/tests/test_diarization.py), [python/whisperflow/tests/test_diarization_models.py](python/whisperflow/tests/test_diarization_models.py), [python/whisperflow/tests/test_writers.py](python/whisperflow/tests/test_writers.py), [python/whisperflow/tests/test_config.py](python/whisperflow/tests/test_config.py)) — still runnable with nothing but `pytest`, `ffmpeg-python` and `numpy`, which is why `import sherpa_onnx` is deferred to the point of use and the model downloader is a separate module. Writing them turned up three defects in the verified reference implementation: smoothing absorbed runs at a segment's edge and then read stale speakers, which inverted short segments wholesale (`[0, 1, 0]` came out as `[1, 0, 1]`); speaker lookup assumed sorted turns and returned a silently wrong answer otherwise; and cluster-id renumbering was unreachable from a test. The writer tests pin the no-label output byte-for-byte, and a differential run over 16 texts × 12 line widths × 3 writers confirmed it matched v1.16.7 exactly — true of the diarization work on its own, but no longer of the release: the wrap fix listed under Fixed deliberately changes every wrapped line, so the byte-identity guarantee now holds only with `max_line_width` left blank, which is how it ships. That narrower claim was re-measured over 33 cases through both the shipped writers and the v1.16.7 ones. Segmentation added 103 more, among them the algorithm run against the real 20.7-second sentence from the specification, and a seeded 200-case property test that asserts text conservation and every hard limit across 1–200 words, Latin and CJK, and line widths of 1, 2, 8, 16, 42 and 80 — width 1 being the important one, since it forces the single-word escape hatch on every token, which is exactly where a naive dynamic program raises or loops forever. Three of them read the source of `transcriber.py` rather than importing it, because importing it needs faster-whisper and CI does not install that; what they pin is the interlock that stops the writer re-wrapping text that already contains line breaks.

- **The TXT paragraph rule is pinned across both languages at once** ([tests/fixtures/txt-paragraphs.json](tests/fixtures/txt-paragraphs.json), [python/whisperflow/tests/test_writers.py](python/whisperflow/tests/test_writers.py), [tests/unit/subtitle-writer.test.js](tests/unit/subtitle-writer.test.js)) — Python writes the `.txt` after a transcription and JavaScript rewrites it after an edit, so the two have to agree byte for byte or saving an edit silently reformats the file. Thirteen cases live in one fixture whose `expected` is the entire file contents, so both suites are doing a byte comparison, and the cases are hand-written rather than generated from the Python output — a generated fixture is a one-sided snapshot that would let a Python regression quietly rewrite its own expectations. On top of that each side reads the other's constants out of its source: changing the two-second paragraph gap in JavaScript alone fails a cross-read of the Python source, and flipping the CJK spacing rule fails a fixture case. Both were confirmed by making the change and watching the test go red.
  **TXT 分段規則由同一份合約同時釘住兩種語言** — Python 在轉錄後寫 `.txt`，JavaScript 在編輯後重寫它，兩者必須逐位元組一致，否則存一次編輯就會默默改掉檔案格式。13 個案例放在同一份 fixture 裡，而它的 `expected` 就是整個檔案的內容，所以兩邊的測試都是在做位元組比對；這些案例是手寫的，不是從 Python 輸出產生的——由程式產生的 fixture 只是單邊快照，會讓 Python 的回歸悄悄改寫自己的期望值。除此之外，兩邊都會從對方的原始碼讀取常數：只改 JavaScript 那邊的兩秒段落間隔，會讓讀取 Python 原始碼的交叉檢查失敗；翻掉中日韓的補空格規則，會讓一個 fixture 案例失敗。這兩件事都是實際改下去、看到測試變紅才確認的。
